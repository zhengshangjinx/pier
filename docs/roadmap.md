# Pier 还能往哪儿长

这份文档只说「下一步做什么」，写给「这一版做完，下一版做什么」那一刻。

收进来的每一条都得通过三个问题：**谁在什么时候会撞上、做成什么样、代价在哪**。
答不上来的不收——「做了大概不错」的东西堆在清单里，只会让真正该做的那几条被淹掉。
明确不做的那些另列一节，理由写在旁边：知道为什么不做什么，比知道要做什么更能说明这是个什么东西。

底下分四摞：**值得做的**（谁疼先做谁）、**顺手要修的**（不是功能，是现状里几处自相矛盾）、
**小件**（攒着一起做）、**明确不做的**。

条目里的文件路径是这次盘点时读到的位置，改过之后可能已经挪了。

## 现状：四个断点

按一条真实的工作流走一遍（起服务 → 看它起来 → 用 → 出问题 → 修），
Pier 断在这四处：

1. **出事之后，最后一步要人自己去翻日志。**
   编译失败给的是 `服务 shop-web 编译失败，详见 ~/.pier/logs/shop-web/2026-10-01.log`
   （`internal/proc/supervisor.go:202`），端口冲突倒是说得很清楚。
   问题是那百分之九十的情况——`EADDRINUSE`、`command not found`、`Cannot find module`——
   都躺在日志的最后几行里，而这一步本来是可以替人做的。
2. **人不在屏幕前就等于没有。** 服务半夜崩了、重启到上限了，界面开着也只在那一条上挂个红字；
   窗口关掉、切走、最小化，「某条服务已经不是能用的状态」这件事传不出去。
   Dock 角标与图标跳动只做了 macOS（`gui/window_darwin.go`），Linux 与 Windows 是空函数。
3. **机器读不懂它。** 所有输出都是给人看的中文表格，没有 `--json`。
4. **编排只到「顺序」为止。** `depends_on` 只管先起后起，前一个起失败了后面照样起；
   探针只有 HTTP GET 一种，所以「等 MySQL 能连了再起」这类事现在表达不出来。

## 一、值得做

### 1. 把日志最后几行读成一句话（启动失败诊断）

**谁会撞上**：任何一次「起不来」。这是这个工具被用得最多的那一刻。
**现在**：能区分「编译失败」「端口被占」「探针没通」，但说不出日志里到底写了什么；
命令行 `pier up` 会跟着 tail 二十行（`logTailLines`），界面里那二十行要人自己去点。
**做成什么样**：`internal/diag`，一个纯文本规则表，扫日志尾部（最后一次运行的那一段），
命中就给两句：**一句原因 + 一句下一步**。规则就是大白话的字符串匹配，第一版盖住这几种：

| 日志里出现 | 一句话原因 | 下一步 |
| --- | --- | --- |
| `EADDRINUSE` / `address already in use` / `bind: address already in use` | 端口被占着 | 看是谁占的 / 换成 `${PORT}` |
| `command not found` / `不是内部或外部命令` / `executable file not found in $PATH` | 找不到命令 | 「SDK 管理」里确认这一套；`pier doctor` |
| `Cannot find module` / `MODULE_NOT_FOUND` | 依赖没装 | 在该目录跑一次装依赖 |
| `UnsupportedClassVersionError` / `invalid target release` | JDK 版本对不上 | 看这条服务选的 Java 是哪一套 |
| `Could not resolve dependencies` | 拉不到依赖（私服 / 代理） | 查网络与 `settings.xml` |
| `permission denied` | 权限不够 | 目录或文件的可执行位 |
| `Killed` / `Cannot allocate memory` | 被系统杀了 | 内存不够 |
| `BUILD FAILURE` / `SyntaxError` / `cannot find symbol` | 编译没过 | 原文最后一行抄出来 |

**判定必须附原文**：界面上除了这句话，还要把命中那一行原样抄在旁边。
规则会误判，用户看见原话才知道该信哪一半——这和 `internal/proc/origin.go` 里
「认不出来就留空，宁可不写也不指一个错的地方」是同一条原则。
**代价与坑**：规则要一条一条攒，别指望一次写全；它是纯字符串函数，
写成表驱动用例（给一段日志、期望给哪一句），改规则不用起服务。
两处消费：界面里挂在错误行下面，命令行 `pier up` / `pier status` 一起打印。
顺手把「进程没了但记录还在」那种状态（`Status.Stale`）也接上——现在那里只有一句「已退出」。

### 2. 服务倒了要有人知道（系统通知）

**谁会撞上**：把服务起起来就去写代码的人——那正是这个工具的用法。
**现在**：Dock 角标（一个数字）+ 图标跳一下，只有 macOS 真的做了，而且角标说不清是谁。
**做成什么样**：宿主进程在「状态从正常转成异常」的那一刻发一条系统通知：
服务名 + 一句原因（用第 1 条的诊断）+ 「已自动重启第 N 次 / 到上限了」。
`notify_darwin.go` / `notify_windows.go` / `notify_linux.go` 各一份，与别的平台差异一个规矩。

- macOS：`osascript -e 'display notification …'`，和 `gui/picker_darwin.go` 走的是同一条路，
  不为一行通知去引 cgo。
- Windows：WinRT 的 toast 能从 PowerShell 5.1 调起来，但脚本的编码要照仓库里
  已经踩过的那条规矩来（`.ps1` 必须带 BOM）。这一条的真实成本主要在 Windows。
- Linux：`notify-send`，没有就静默不做。

三条硬要求：**只发真出事**（异常退出、重启到上限、启动失败），不发更新、
不发「检查过了」——仓库里已经有过结论：「网络不通就弹框只会让人烦」；
**给一个开关**（偏好设置「通用」里一项，默认开）；**发不出去要静默降级**，
通知失败不能让界面报错。
**代价与坑**：三份平台代码，且都要能退化成「什么都不做」。
Pier 拿不到退出码与信号（进程是 `Release()` 之后不 Wait 的），
所以通知里那句话只能来自「什么时候不见的 + 最后几行日志」——
这已经够用，别为了退出码去改进程模型（见「明确不做」）。

### 3. 机器读得懂：`--json` 与能信的退出码

**谁会撞上**：脚本、AI，以及任何想把 Pier 接进别的东西里的人。
**现在**：输出是中文表格；`pier up` 会等到全部就绪才返回、有一个没起来就返回 1
（这点是对的，别动）；但端口被占的服务是「跳过」，既不算失败也不进 `failed`，
**最后一个错都没有时 `up` 返回 0**——脚本会以为起来了。
**做成什么样**：

- `status` / `ports` / `doctor` / `logs --size` 加 `--json`，输出的字段**直接用
  `internal/panel/state.go` 那份 `StateOut`**，不另定义一套形状（它顶上那句
  「JSON 键名属于对外合同」就是为这个写的）。
- `pier logs <服务> --tail N`：现在固定一百行（`logTailLines*5`），`--since` 可选。
- `pier logs a b c`：现在一次只收一个服务名，而查一个问题常常要连着看三个。
- `pier wait <服务>`：等就绪或超时，退出码说话。`proc.WaitHealthy` 已经在，
  `up` 内部走的就是它，单独开一个动词几乎是白捡——它是 AI 最需要的那个动作
  （起 → 等 → 拉日志），现在只能靠 `up` 的隐式等待。
- **跳过也算没达成**：`up` 结束时把「跳过」单列一节，退出码给非 0。
  退出码写进 `--help` 与 README，照 `pier update --check` 那套（0/10/1）的样子来。
- **顺手把已经说反话的几处对齐**（都是退出码，不是新功能）：

  | 现在 | 发生什么 | 该怎么样 |
  | --- | --- | --- |
  | `pier up`，端口全被占 | 逐条打「跳过」，收尾说「没有启动任何服务。」，退出 **0** | 跳过单列一节，退出码非 0 |
  | `pier logs --clean <正在跑的服务>` | 说了「正在运行，先停下再清理」，退出 **0** | 原因留着，退出码说「没清成」 |
  | `pier doctor` | 缺工具也退出 **0**（源码里写明是刻意的：只用到 Go 的服务照样起得来） | 语义不动，让 `--json` 把「缺了哪些」交出去，脚本自己判 |
  | `pier --version` | 「未知命令」，退出 2（只有 `pier version` 能用） | 认一下这个写法 |
  | `pier up --help` | 被当成一个服务名，报「没有名为 --help 的服务」 | 每个动词认 `-h` |
  | `pier status 多余参数` | 位置参数被静默忽略，退出 0 | 报错（也许是打错字的服务名） |

  **`pier down` 的例外要留着**：「不是 Pier 起的」与「已经退出」只提示、退出 0，
  这是对的——重复执行 `down` 本来就该是安全的。别一刀切成「没做成就是 1」。

**代价与坑**：几乎没有实现代价，但**每多一个字段都是一份对外承诺**，
第一版宁少勿多；`--json` 之后那些字段就不能再改名字了。

### 4. `pier mcp`：把本地接口包成 MCP server

**谁会撞上**：用 Claude Code / Cursor 开着这个项目写代码的人——起服务、等就绪、拉日志，
现在全靠「先知道有 `pier` 这个命令，再解析中文输出」。
**现在**：`pier api` 已经是一张九条路的接口（`internal/api/api.go:188` 的 `routes`），
每个请求都要令牌，还有一份由 routes 生成的 OpenAPI 3.1。
（「只监听回环」是它的设计前提，但 `--addr` 现在能把这个前提破掉，见「二、顺手要修的」。）
**做成什么样**：`pier mcp`，stdio，把那张表映射成 MCP 的 tools：
`list_services` / `service_status` / `start_service` / `stop_service` /
`restart_service` / `read_logs` / `wait_ready`。**走 stdio，不开端口、不发令牌**——
用它的进程就在本机，多开一个端口就多一份要保护的东西。

**前提是接口自己得先够用**：现在那九条路全是「一次一个服务」——没有分组、没有批量，
也没有「等服务就绪」（`POST …/start` 返回 202，之后要自己轮询 `/api/state`）。
所以第 3 条里的 `pier wait`、第 9 条里的分组，得先进 `internal/api`；
MCP 那一层只是搬运，接口没有的东西包不出来。
**代价与坑**：MCP 的 stdio 就是 JSON-RPC 2.0 上的 `initialize` / `tools/list` / `tools/call`
三个方法，自己写两三百行、且能单测；仓库为一次版本比较都自己写了（`internal/version`），
这里也不值得引一整套 SDK。但**协议版本协商、`tools/list` 的参数 schema、
错误的写法**这三处要照规范来，不能自己发明。
顺序上它排在第 3 条后面：`--json` 做完，这一层就只是搬运；
而且它真正的价值（工具被递到手上，而不是让人去猜）要等有人真的用它才成立。

### 5. 依赖不只是顺序（`depends_on` 的 condition 与探针类型）

**谁会撞上**：后端要等数据库 / 注册中心 / mock 服务起来才活得下去的人。
**现在**：`depends_on` 只排序，前一个起失败了后面照样起（`config.go` 的注释写明了这是刻意如此）；
探针只有 HTTP GET（2 秒超时、500ms 一次、180 秒窗口）。
**做成什么样**：

- 探针加两种：`tcp://host:port` 与 `cmd: <命令>`（退出码 0 即就绪）。
  没有 tcp 就谈不上「等 MySQL 能连了」——它没有 HTTP 接口。
- `depends_on` 支持带条件：`depends_on: [mysql:healthy]`（或在字段里写对象，
  语法看哪个更顺手）。**只等声明了条件的那几条**，其余照旧并行拉起，
  否则一个 Java 服务会把整条链的时间串起来（`cmdUp` 顶上那段注释就是为这件事写的）。
- 等不到怎么办：**照旧起，把「依赖 X 没等到」写在这一条的状态里**。
  理由和探针过期那条一样（`panel.go:546`）：服务已经在跑了，
  卡在那儿不动比「起了并说清楚」更难解释。

**代价与坑**：condition 会改变现在「全部并行拉起、再统一等」的时序，
改动落在 `panel.startOne` 与 `cmdUp` 两处，测试要盯住「总时长不被串行化」。

### 6. 环境变量：共享、`.env`、`${}` 展开

**谁会撞上**：多项目本地开发的人，尤其是有代理、私服、统一 `TZ` 的那类环境。
**现在**：`buildEnv` 只做三件事——继承 Pier 的环境、合入工具链变量（`JAVA_HOME` 等）、
追加服务自己的 `env`。没有共享段；不读 `.env`（`.env` 只被 `probe.go` 用来**猜端口**）；
`${VAR}` 原样传给子进程。
**做成什么样**（三件事各自独立，可以分开做）：

- **共享一组变量**：清单顶层 `env:`，所有服务都拿到，个别服务覆盖它。
- **读 `.env`**：服务目录下的那份自动注入，语义照 `dotenv` 的通行做法
  （不覆盖已有的、去掉两端引号、`#` 起注释）。只读 `.env` 这一份，
  不替项目决定 `.env.local` / `.env.development` 该取哪个——那正是各个框架自成一套的地方。
- **`${}` 展开**：从「已经算好的环境」里取（含共享段与工具链变量），`${PORT}` 取服务的端口。
  展开失败**报错而不是留空**：留空会静默把一个空值启动成一次诡异的失败，
  而报错一行就说明白了。

**代价与坑**：展开只能显式触发（写了 `${}` 才展开），不能把用户原样的值改掉；
`${PORT}` 这一条是下面「端口让路」的前提。

### 7. 端口：让路，但要说出来

**谁会撞上**：同时开着几个项目、8080 被别的东西占着的人——这是本地开发最常见的失败之一。
**现在**：端口被占 → 界面报错、命令行跳过；`FreePort` / `PortCandidates`
只在**新建服务时**用；端口不会注入成环境变量。
**做成什么样**：分两步走，第一步就够用——

1. **界面上给一颗「换一个端口起」**：找一个空端口，把这次启动用的端口换成它，
   界面上显示成「清单里写的是 8080，这次用的是 8081」。依赖第 6 条的 `${PORT}`。
2. 再考虑 `autoPort: true`（自动让路）。**默认不做**：默默换端口比失败更糟——
   失败了至少知道，悄悄换了之后，前端代理还指着 8080。

**代价与坑**：实际端口必须一直显示在界面上，包括日志头部那句「运行：」；
一次运行换一次，不写回清单。

### 8. `watch`：改完自动重启

**谁会撞上**：这个项目立项理由里的那句话——「改完就要重启看效果」。
**现在**：没有文件监视（`go.mod` 里没有 fsnotify，全仓没有 watcher）。
**做成什么样**：清单里一行 `watch:`，变化后合并 400ms 再走一次正常重启；
`watch: true` 时按类型给一套默认（go → `**/*.go` + `go.mod`，java → `src/main/**`）。
**代价与坑**：air / nodemon 踩过的坑这里一个都跑不掉——**必须排除产物目录**
（`node_modules`、`target`、`dist`、`.git`，还有日志与 `BinDir`），
否则编译产物一落地就自激；前端 dev server 自己会热更，别重复；
监视只在持有 `restart.lock` 的那个宿主里做。
没有 fsnotify 就得轮询 mtime，一秒扫一棵源码树在 macOS 上可以接受，先这样。
价值是「不用为每个项目各配一遍，而且 Pier 本来就知道每个服务是什么」——
它和 air / nodemon / devtools 是重叠的，别把它说成新东西。

### 9. 启动哪一批：分组成为一等公民

**谁会撞上**：清单里躺着几个平时不需要的服务（mock、抓包、只在前端调试时用的那一套）的人。
**现在**：分组是**界面上的口径**——界面上选中某个分组，顶栏的批量启停跟着当前这一页走；
命令行按不了它（`pickServices` 只认服务名，`cfg.Find` 只认 `name`）。
「全部启动」就是清单里的全部，没有例外（`pier.user.yaml` 的 `hidden` 能做这件事，
但那是 YAML 清单模式才有的路）。
**做成什么样**：

- `pier up @前端`（或 `--group 前端`）：与界面上那一页对齐。
  注意内置的「未分组」不能被当成用户分组（`GroupOut.Builtin` 已经有这个区分）。
- 服务上一颗「不参与全部启动」的开关（`manual: true`）：
  `pier up` 不带名字时跳过它，点名时照起。

**代价与坑**：小。要防的是「全部」多出第二种含义——现在的「全部」是清单全部，
加了 `manual` 之后是「参与全部的那些」，界面上要写清楚（比如概览那里写「M 个参与全部启动」）。

### 10. 第一次打开它的人：把 `detect` 搬进界面

**谁会撞上**：陌生人第一次打开这个应用（以及开源之后从 Releases 下来试的人）。
**现在**：新服务是一张空表单；`pier detect` 只有命令行有；
`DeriveFacts`（读 `config.yaml` 的 `server.port`、Spring 的 `application.yml`、
`.env` 里的 `PORT`）在界面里只体现为「填完目录后自动带出端口」。
**做成什么样**：空清单时的第一屏不是空白，而是「选一个目录，我扫一遍」：
列出认出来的项目（名字、类型、端口、依据），勾选后一次全加。
新建服务的表单里也放一颗「从这个目录猜一下」。
**代价与坑**：`internal/config/detect.go` 与 `probe.go` 已经是纯函数，搬进 `manage` 即可，
难的是**界面上怎么摆「依据」**——猜出来的东西必须写着它凭什么猜的，
否则用户不敢点「全部添加」。

### 11. 清单也能从命令行与接口改

**谁会撞上**：让 AI 加一条服务的人；以及任何想「脚本里把这条服务的端口改了」的人。
**现在**：`pier import` / `pier detect` 能**读**出服务定义并打印成 YAML，
但落盘只能靠「复制成 YAML、再手改那份 JSON」；`EnsureStore(store, yamls)`
（把 YAML 导入数据文件）早就写好了，**目前只有测试在用**。
而界面里那几件要命的小事——端口查重、目录校验、改名时日志目录跟着搬、
正在跑的服务不许删——命令行一样都没有。
**做成什么样**：`pier add`（`--name` / `--dir` / `--kind` / `--port`，不带参数就从当前目录猜）、
`pier rm <服务>`、`pier edit <服务> --port 8081`，外加 `pier group`。
校验一律走 `internal/manage` 已经有的那一份（`SaveService` / `DeleteService`），
不另写一套——端口撞车、目录存不存在、`~` 不许出现、删之前要不要先停，规则全长在那里。
**代价与坑**：改文件的和读文件的是两个进程，而**界面只在启动与切换清单时读一次**
（`panel.Load` 只有 `gui/app.go:63` 与 `gui/manage.go:253` 两处）——
命令行加了一条，已经开着的窗口里看不见，得重开才知道。
所以这条要么先说清这个限制，要么顺带做「宿主定时重读清单」：
改文件的是外部进程，只能轮询；两秒读一份 JSON 很便宜，真正要想清楚的是
「用户正在编辑这一条，而文件刚被外面改掉」该怎么处置。
**第一版建议只做命令行，并明说「重开窗口生效」**——比做一个让人丢编辑的半吊子同步好。

## 二、顺手要修的（不是功能，是现状里自相矛盾的地方）

都不大，但每一处都在用户会撞到的地方。按「撞上之后有多难受」排：

- **`pier api --addr 0.0.0.0:7717` 真的能绑到全网卡**（实测：`--addr 0.0.0.0:17717`
  起出来的是 `[::]:17717`，`lsof` 里写着 `TCP *:17717`，局域网可达）。
  `parseApiArgs` 收下 `--addr` 后原样交给 `net.Listen`，没有任何校验，而 README
  把「只监听回环」写成两条硬约束之一——理由写得很清楚：这个接口能启停进程，
  绑到 `0.0.0.0` 等于把「在这台机器上跑什么」交给整个局域网。
  `api.go` 里 `baseURL` 那句注释说明写的人想过这茬，只是没拦。
  **只让回环通过**：`--addr` 要么去掉，要么只接受 `127.0.0.1` / `::1` / `localhost`
  这几个值，别的当场报错。
- **README 的 `--config` 例子是错的**：写着 `pier --config ./pier.yaml status`，
  实际会得到「未知命令：--config」加退出码 2——`--config` 只能跟在动词后面
  （`extractConfig` 在 `args[1:]` 里找）。正确的是 `pier status --config ./pier.yaml`。
  「所有子命令都接受 `--config <清单>`」这句也要改：是「每个动词都接受」，
  不是「随便哪个位置都能写」。
- **`pier --help` 里没写 `--config` 与 `api --addr`**（`usageText` 只列了动词），
  而这两样正是这份 README 在教人用的东西。
- **`renameService` 是一段死接口**：`gui/manage.go:82` 那条改名路径只挂在
  `pierRenameService` 上，而界面（`app.js:43`）绑了它却从来没调用过——
  真正的改名走的是 `saveService` 带 `OrigName`（`manage.go:351` 那段注释写明了为什么
  合成一次 commit）。要么删掉这条绑定，要么把界面的改名接回去；
  现在这样是「看得出来改过名，但看不出来谁在用」。
- **`pier logs` 的几个开关互相压**：`--size` 在 `--clean` 之前判（`--clean --size`
  只看大小，不清理）；`--all` 只在 `--clean` 下有人读，别处给了它也不说一声。
- **`build` 字段在 Node / Python 上被静默忽略**（`planNode` / `planPython` 从不读它），
  而表单里有这个字段。要么实现，要么在界面上说明这两类不用它——
  别让它摆在那儿装作有用。
- **`pier up` 在端口被占时返回 0**：见「一、值得做」第 3 条，那里单列了一节。
- **`restart.lock` 只在 `panel.New` 里抢一次**（`internal/proc/claim.go`）：
  持有它的那个窗口退出后，其它开着的窗口不会接管，自动重启就静默停了。
  改成定时重试抢一把。
- **自动重启的次数记在内存里**（`[]time.Time`），界面重开一次就归零，
  于是「已经重启三次了」这件事会丢。
- **`health` 地址没有格式校验**：写成 `localhost:8080/health`（少了 scheme）会永远探不通，
  一路走到「探针过期」才被人发现——在表单里挡一下比事后查便宜得多。
- **日志单日没有大小上限**：一个刷屏的 dev server 一天能写几百兆，
  十四天的保留期会把磁盘吃掉。要么封顶、要么超限时提醒。

## 三、小件（攒着一起做）

- **记住上次停在哪一页**，以及**窗口的尺寸与位置**。现在 `settings.json` 里只有主题、
  两个更新相关的键，重开一次就回到「全部服务」和默认大小。
  窗口那个有现成的坑：`defaultWindowSize` 是按主屏可用区域算比例再收进上下限的
  （写死尺寸在小屏顶满、大屏局促），存下来的外框必须照样过一遍这个收敛，
  还得处理「上次那块屏已经不在了」。
- **主体里按分组折叠**：侧栏已经能选分组，但「全部服务」那一页仍是一长条。
  几十个服务时这是滚动比赛。
- **日志导出 / 另存**：界面上的「复制全部」复制的是**已经读进内存的那一份**，
  而日志抽屉只加载尾部——大文件时复制出来的并不是全部，这件事得说清楚或者补一个导出。
- **CPU / 内存的历史曲线**：`panel` 每两秒采一次，只是没留。内存里存最近几十个点就能画。
  **只放内存**，不落盘——真要落盘得先想清楚写在哪、留多久（那是另一条日志）。
- **搜索范围**：现在只搜名字、目录、端口，加上备注与分组名是几行的事。
- **「已停止」筛选**：现在有「全部 / 在跑 / 异常」，缺一个「没在跑」。
- **批量勾选**：目前是「这一页全启全停」。如果第 9 条的分组够用，就别做勾选——
  勾选是一次性动作，分组是可复用的；两套并排摆着，人会先猜它们有什么区别。

## 四、明确不做

- **菜单栏 / 托盘常驻**：三平台就得三套原生代码（这条底线不能破），
  而菜单栏的价值主要在 macOS——只做一边，正是这个仓库一直在防的事。
  真正想要的东西是「不在场也知道」，那个用通知解决，代价小一个数量级。
- **接管 docker compose / 容器**：那是另一套生命周期——停止是 `docker compose stop`，
  不是给进程组发信号；日志在 docker 手里，不是一个个文件。
  能做而且值得做的只有一件小事：`pier ports` 认出来「这个端口握在某个容器手里」
  （问 `docker ps`，问不到就留空），但**不去启停它**。
- **远程 / 多机 / 团队共享的服务端**：有了第二台机器，就多出账号、传输、离线这一整套；
  而这个工具的全部好处来自「它就在你本机上」。
- **开机自启、常驻守护**：和「服务不随 Pier 退出」是两件事，混在一起会让人
  以为 Pier 是个守护进程——它不是。
- **精确的退出码 / 信号 / OOM 记录**：要拿到它就得把服务挂回 Pier 底下（`Wait`），
  那会毁掉「关掉 Pier，服务照跑、日志照写」这条根。
  够用的是「什么时候不见的 + 最后几行日志」，这两样都拿得到。
- **界面英文（暂时）**：这个界面的文案是信息量本身（每条错误都写着下一步该干嘛），
  直译会丢掉一半。真有人在 issue 里要再说。
- **主题色、插件系统、更新渠道（beta/稳定）**：理由在 `AGENTS.md` 与上一版计划里写过，
  没变。

## 五、如果只做三件

1. **第 1 条 + 第 2 条一起做**：诊断与通知是同一件事的两半——
   出事了要知道，知道了要看得懂，而通知里那句话正是诊断给的。
   这两条加起来，日常最难受的那一段（服务偷偷死了/起不来）就有解了。
2. **第 3 条**：最便宜的一条，而且是后面所有自动化（包括第 4 条）的地基。
3. **第 6 条**：多项目本地开发里最常要抄来抄去的东西，抄一份就有一处会对不上。

其余按「谁疼先做谁」。第 5、7、8 条都建立在一个前提上——
服务之间真的开始有依赖与端口冲突了；如果日常还没到那一步，先放着。

**但「二、顺手要修的」里有两条不用等排期、也不该等**：
`pier api --addr` 的口子（一条命令就能把「能启停进程的接口」挂到局域网上），
和 README 里那个跑不通的 `--config` 例子（第一个照着敲的人就会撞上）。
这两条随时可以做，加起来不到半小时。
